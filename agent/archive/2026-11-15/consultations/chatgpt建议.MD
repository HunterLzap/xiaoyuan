# 个人 AI 助理连续语音方案：技术选型与实施建议

资料核验日期：2026 年 10 月 31 日。价格以公开官方文档为准；实际可用性、音质和延迟仍需实测。

## 一、先给结论

最推荐：暂时保留 ASR → LLM → MiMo TTS 架构，先把网页改成真正的连续、双向语音交互系统；同时用原生实时语音 API 做独立对照测试，再决定是否迁移。

这里的重点不是继续优化原来的“点击录音—发送—播放”流程，而是将其升级为：

- 麦克风持续采集，自动判定用户是否说完。
- AI 播放期间仍接收、分析用户语音。
- 通过回声消除、说话人判断和插话确认，决定是否打断。
- 播放、识别、模型生成分别拥有可取消的任务状态。
- 文字消息、语音播报和 SQLite 历史统一管理。

### 两条路线的建议

|                      | 主推荐：改造现有级联         | 替代：原生实时语音                         |
| -------------------- | ---------------------------- | ------------------------------------------ |
| 架构改动             | 较小，复用现有能力           | 中到大，需要实时协议适配                   |
| MiMo 克隆音色        | 可直接保留                   | 取决于供应商，不能直接迁移音色 ID          |
| 自然断句             | 需要补齐回合检测             | 可使用供应商内置机制                       |
| 普通外放打断         | 需要重点开发                 | 仍需客户端 AEC，部分服务提供更强的插话判断 |
| 接话延迟             | 有优化空间，但仍存在级联耗时 | 通常更有潜力减少等待环节                   |
| 现有角色、工具、历史 | 最容易保留                   | 能保留部分能力，但需要适配                 |
| 2 核 2GB 云服务器    | 适合云端推理、轻量编排方案   | 适合轻量代理方案                           |
| 最大不确定性         | 双讲处理和端到端延迟         | 中文效果、克隆音色、价格及服务端控制       |

我建议把“保留级联”作为主项目路线，把原生实时语音作为受控的替代实验，而不是立即重构。

原因是你已经具备流式 LLM、流式 TTS、声音配置、取消机制和 SQLite 历史。当前最明显的缺失集中在音频输入与回合控制层，而不是全部模型能力。

另外，官方资料已经确认，Seeduplex 已有火山引擎 API 文档；阿里云也公开提供带语义轮次判断的 Qwen-Audio Realtime 服务。这两类方案值得作为真实候选，而不只是参考技术演示。

docs.volcengine.com+1



## 二、最需要明确的架构区别

原生语音模型 ≠ 完整的全双工语音系统 ≠ 普通外放下可靠打断。

这三个层次解决不同问题：

浏览器音频层

持续收音 · AEC 回声消除 · 降噪 · 音量检测 · 播放控制

实时会话控制层

轮次检测 · 插话判定 · 取消旧回答 · 历史同步

级联模型

ASR → LLM → TTS

原生语音模型

音频输入 → 联合处理 → 音频输出

对于你的项目，不论采用哪种模型路线，浏览器音频层、会话控制、UI 和历史管理都是必须解决的工程工作。

原生模型的主要优势是可能减少中间处理与等待，并利用语音语义、语调和上下文辅助判断。但它不能保证物理扬声器播放的 AI 声音不会被麦克风重新录进去。后者仍取决于客户端音频处理与模型侧策略的配合。

## 三、真正的技术卡点与解决方案

### 1. 接话速度：不能只看首 Token

你要求的延迟，应该从用户最后一个有效语音采样结束，到扬声器真正开始播放 AI 的声音计算。

级联链路的时间可以拆成：

\[ T_{\text{总}} \approx T_{\text{判停}}+T_{\text{ASR最终确定}}+T_{\text{首段文本}}+T_{\text{TTS首音频}}+T_{\text{播放}} \]

这里的五项不是在所有实现中都严格串行。例如流式识别可以提前处理语音，预生成可以在确认轮次前启动 LLM。

| 环节       | 你当前的情况        | 建议                                   |
| ---------- | ------------------- | -------------------------------------- |
| 确认说完   | 网页依赖手动结束    | 引入 VAD + 语义/声学判停               |
| ASR        | SenseVoice 整段识别 | 先考虑自动切段，必要时换真正的流式 ASR |
| LLM 首段   | 已有流式输出        | 测量到“首段可播报文字”，而非首 Token   |
| TTS 首音频 | MiMo 已有流式播放   | 测首个可解码 PCM 包的到达时间          |
| 播放       | 浏览器 PCM 队列     | 降低预缓冲，检查音频队列和播放调度     |

现阶段最可能的大问题是手动结束与缺少自动判停。去掉这个缺口后，真正的瓶颈可能变成 LLM 首段或 TTS 首音频，不能凭现有描述断言哪个最慢。

#### SenseVoice 怎么处理

SenseVoice 的常见本地推理用法属于整段音频识别，不应因为它处理得快，就把它当成真正的流式 ASR。

有三种选择：

1. 最小改动： VAD 检测出候选语音段后，将音频送给现有 SenseVoice；判停前也可以对候选音频做非正式识别，用于辅助判断。这是重复执行整段识别，不是真正的流式解码。
2. 保留级联、换实时 ASR： 采用支持连续音频输入、部分转录和最终转录事件的服务，例如 `qwen3-asr-flash-realtime`、`fun-asr-realtime`，或者流式 Paraformer。
3. 改用原生实时语音： 将音频连续送到实时服务，由服务维护输入、回合检测及语音生成；应用层仍保留文字历史和取消控制。

对你而言，第二种最适合作为级联路线的长期形态；第一种适合验证交互流程。

#### LLM 与 TTS 应怎样优化

- 首 Token 不是关键指标。 例如模型很快输出“我”，但迟迟未形成可播报短句，TTS 仍然无法产生有意义的第一段语音。
- 首段策略优先使用短句、标点和语义边界。 同时允许在合理的最短文本长度后提前切段，避免等待完整长句。中文不能机械地每固定几个字切一次，否则音调和停顿会不自然。
- 首段生成与后续生成重叠。 TTS 处理第一段时，LLM 继续生成下一段；音频只做适量预缓冲，避免累计很长的待播报队列。
- 可尝试预测性生成。 在流式 ASR 给出较稳定的内容时提前启动 LLM，但只有判停确认后才播放，发生续说就丢弃预测结果。

更换低延迟文本模型只减少 LLM 部分；如果判停慢、TTS 等待首段或者网络绕路，收益可能很小。

原生实时语音的潜在收益在于不必每次等待明确的“最终识别文字 → LLM 首段 → 独立 TTS 首包”全部完成。但它仍有内部推理、音频生成、网络传输和实际播放延迟。

### 2. 自然断句：VAD 是第一层，不是最终答案

| 方法                    | 能解决的问题                 | 关键不足                         | 建议             |
| ----------------------- | ---------------------------- | -------------------------------- | ---------------- |
| 固定静音时间            | 实现简单                     | 停顿长短无法自适应               | 只作基线         |
| Silero VAD              | 判断是否存在语音活动         | 不理解说话意图与轮次结束         | 保留作基础检测   |
| 流式 ASR endpointing    | 利用转录进度和供应商终点信号 | 能力因识别服务而异               | 级联路线推荐     |
| 文本语义判停            | 判断表达是否完整             | 依赖稳定转录，可能增加推理和等待 | 与 VAD 组合      |
| Smart Turn 一类音频模型 | 利用语音声学特征及语调判断   | 有 CPU 开销，中文效果需要验证    | 级联路线优先实验 |
| 实时模型内置判停        | 供应商统筹声学、语义、上下文 | 可调性和行为受供应商限制         | 原生路线优先使用 |

推荐的级联决策方式：

持续音频输入

VAD 检测语音开始与候选停顿

流式 ASR / 音频回合模型判断是否结束

尚未说完

继续收音，保留当前音频与转录上下文

确实结束

提交最终转录，触发或确认 LLM 回答

目前有两类值得直接参考的实现：

- Pipecat Smart Turn v3：结合 Silero VAD，在候选停顿后分析近期音频，辅助判断轮次完成；有本地 ONNX 推理实现。
- LiveKit Agents：除了轮次检测，还区分正式插话和附和声，并支持误打断后的恢复。

LiveKit 当前官方音频 Turn Detector 已支持中文；旧版独立 `livekit-plugins-turn-detector` 已被标为弃用，不能再把旧插件当成首选。

### 3. 普通外放打断：重点是 AEC 与插话判断分层

你明确拒绝的两种做法——强制戴耳机、AI 播放期间关闭麦克风——都不是这项功能的必要前提。

正确的信号链是：

麦克风输入

本人声音 + AI 外放回声 + 环境噪声

AI 播放参考

当前实际送到扬声器的 AI 音频

AEC / AEC3 + 残余回声抑制

尽可能消除 AI 播放音频在麦克风中的回声，保留近端真人声音

降噪 + VAD + 插话意图判断

检查是否是本人有意义的讲话，而非敲击、回声或附和

确认插话 → 本地立即停止播放 + 取消后端旧回答

AEC 最关键的机制，是同时利用近端麦克风音频和远端播放参考音频。WebRTC Audio Processing 官方接口明确区分 `ProcessStream()` 和 `ProcessReverseStream()`，后者就是回声处理所需的播放参考路径。

Git at Google+1



因此，不是“使用 WebRTC 就一定不会回声”，而是需要确保所用的音频采集及播放路径真正启用了相应处理。

### 4. 浏览器 AEC：你的 PCM 播放方式需要专门验证

现有 `Web Audio API + PCM 队列` 不代表浏览器 AEC 一定失效，也不代表一定有效。

浏览器内建 AEC 通常通过麦克风采集链路处理回声；它能否正确获得 AI 的播放参考，与浏览器、操作系统、音频输出路径以及采集方式有关。普通的 `AudioContext.destination` 播放可能被浏览器纳入回声参考，但不能把这一点当成跨浏览器保证。

建议开发者按以下顺序处理：

1. 先验证内建 AEC。 保留 `getUserMedia` 的 `echoCancellation: true`、`noiseSuppression: true`，增加 `autoGainControl` 的针对性测试。用 `MediaStreamTrack.getSettings()` 检查协商结果，但它只能证明配置状态，不能证明回声消除效果。
2. 对比两种播放路径。 一种是当前 `AudioContext` PCM 队列；另一种是标准 `` / WebRTC 远端音轨播放。分别录制处理后的麦克风信号，比较 AI 单独播放时的回声残留，以及真人与 AI 同时讲话时真人语音的保真度。
3. 如果内建 AEC 不足，再考虑 WebRTC Audio Processing / AEC3。 自定义处理时，把实际播放的音频作为 reverse stream 参考，把麦克风信号作为 near-end stream，处理音频延迟对齐、双讲和残余回声。优先放在用户设备侧，而不是依赖远端云服务器去猜测扬声器延迟。
4. 不要盲目叠加两个 AEC。 浏览器 AEC 与自建 AEC3 的组合，需要比较处理前后的效果；重复消除可能损害近端说话人的声音。

参考：[WebRTC Audio Processing API（处理流和反向参考流）](https://github.com/mozilla/webrtc.org/blob/master/webrtc/modules/audio_processing/include/audio_processing.h?utm_source=chatgpt.com)。

#### WebRTC 与 WebSocket 怎么选

- WebSocket： 对你的原生 JS + FastAPI 项目最容易接入，可同时上传 PCM 小帧、接收文本事件和播放音频。AEC 仍依赖浏览器采集链路或独立 DSP。

- WebRTC： 更适合实时音频传输、抖动缓冲、丢包处理和浏览器音频轨道对接，但不保证自定义播放路径一定具有可靠 AEC。

- AOQ 等厂商专用音频协议： 可能集成更完整的音频前处理。阿里云 Qwen-Audio 官方文档明确推荐 AOQ 用于更重视弱网、低延迟、全双工降噪及回声消除的接入；但它需要适配专用客户端 SDK，不能将普通 WebSocket 改个地址就获得同样效果。

  help.aliyun.com

  

工程建议：先用 WebSocket 完成对话控制，再通过实际双讲测试决定是否调整播放路径或增加 AEC3。 不应在没有证据前把整套项目迁往 WebRTC。

### 5. 如何防止误打断，又能及时插话

我建议实现一个“候选插话 → 确认插话”的小状态机，而不是把 VAD 的 `speech_started` 直接映射成取消回答。

| 事件                       | 推荐行为                                               |
| -------------------------- | ------------------------------------------------------ |
| AI 播放时发生短暂声响      | VAD/降噪过滤，继续播放                                 |
| 检测到疑似真人开始说话     | 可立即短暂压低或暂停播放，继续听取和识别               |
| 识别为持续、相关的用户讲话 | 确认插话，取消旧回答                                   |
| 识别为咳嗽、短促“嗯”、回声 | 恢复旧回答，不丢弃播报进度                             |
| 用户按“停止回答”           | 立即停播放并取消生成，不需要语音判断                   |
| 用户按“麦克风静音”         | 停止向 ASR/实时模型提供有效麦克风输入，AI 播放不受影响 |

候选插话的声学判断要快；语义确认可以稍慢。两者结合才能兼顾“迅速安静下来听你说”和“不因误判永久取消整段回答”。

确认插话时必须同时做两件事：

- 前端立刻执行： 停止正在播放的 `AudioBufferSourceNode`，清空 PCM 待播队列，丢弃旧轮次的后续音频包。
- 后端立即执行： 取消对应 `turn_id` 的 LLM/TTS 任务，必要时向供应商发送取消事件；后续迟到的数据包按轮次编号丢弃。

如果只取消后端，浏览器已缓存的音频仍可能继续说话；如果只停浏览器，后端可能继续生成、收费，并把旧文字写入会话。

对原生实时 API，也需要处理其 `response.cancel`、`response.done`、本地播放清空及必要的对话内容截断，避免模型错误认为自己已经把未播放的内容说完。

### 6. 抗干扰必须分成两类

| 干扰                   | 主要技术                                          | 能否保证识别成“不是我”       |
| ---------------------- | ------------------------------------------------- | ---------------------------- |
| 风扇、空调、键盘、敲击 | 降噪、VAD、时长和置信度过滤                       | 通常可明显改善               |
| AI 自己的外放语音      | AEC、残余回声抑制、双讲处理                       | 取决于参考音频与实际声学条件 |
| 电视或视频中的人声     | 目标说话人识别、声纹、语音分离、位置/距离特征     | 不能仅靠 Silero VAD          |
| 旁边真人讲话           | 目标说话人验证、麦克风指向性、个性化唤醒/意图策略 | 仍可能误判                   |

尤其要注意：AEC 能消除它拥有参考信号的 AI 播放回声；通常不能直接消除另一台电视机发出的陌生人声。

若电视、旁人讲话确实频繁，建议把“目标用户声纹”作为可选增强层。Qwen-Audio 的 `smart_turn_v2` 与说话人增强能力值得实测，但声纹不是可靠的人声分离替代品，也不能保证所有声学环境都正确。

## 四、部署与现有功能如何保留

### 1. 2 核、2GB 云服务器：按任务分配判断

| 方案                                   | 云服务器要运行什么                                      | 2 核 2GB 的判断                                              |
| -------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------ |
| 本地 SenseVoice + 现有级联             | SenseVoice 推理、FastAPI、音频处理、SQLite              | 不应直接认为够用；模型加载内存、并发峰值、CPU 推理需要 Linux 实测 |
| 云 ASR + 网关 LLM + MiMo TTS           | FastAPI、WebSocket、音频转发、状态控制、SQLite          | 个人单会话较有希望，但需计入 Python 进程、TLS 和网络缓冲     |
| 原生实时云 API                         | FastAPI 代理/鉴权、WebSocket 或 WebRTC 会话管理、SQLite | 个人单会话较有希望；重型客户端音频处理不应搬到这台云主机     |
| 在云端跑 ASR + 声纹 + Smart Turn + AEC | 多个本地推理和信号处理模块                              | 2GB 风险明显升高，尤其多个 ONNX/PyTorch 运行时同时加载       |

对主推荐路线，我倾向于：将持续收音、基础 AEC、音量波动放在浏览器；语音识别与模型推理放在线服务；2 核 2GB 主要做轻量编排。

Silero 可在浏览器经 ONNX Runtime Web/WASM 运行；Smart Turn 可以在 Python 服务端使用 ONNX，但需要单独测试延迟与内存。它的模型文件大小并不等于完整进程内存；ONNX Runtime、Python、WebSocket 缓冲和其他 worker 都会占资源。

### 2. 音色与角色

原有 MiMo 克隆音色是保留级联架构的重要理由。

但迁移原生语音并不一定意味着失去声音复刻：

- Qwen-Audio 3.1 Realtime 明确支持创建克隆音色，并用新的 `voice_id` 配置输出。仍需重新复刻、对比相似度和中文表现。

- Seeduplex 的会话协议支持复刻音色 ID；具体复刻和槽位费用需另算。

- OpenAI Realtime 的 `gpt-realtime-2.1-mini` 支持符合条件的录音复刻音色，但官方将录音创建权限限定为获准客户，且需要声音授权录音。不能假设个人账号已经有权限。

  help.aliyun.com+3

  

还有一个折中方案：使用原生实时模型做语音理解、回合检测和文字生成，却继续把文字交给 MiMo TTS 播放。

这在技术上可以做，但要注意，它重新增加了独立 TTS 的首包延迟，也可能使模型原本的端到端语调、情绪和语音连续性优势大幅减弱。除非 MiMo 音色不可替代，否则不建议把它作为原生路线的默认实现。

### 3. 界面与历史不依赖模型架构

建议前后端始终使用同一个 `conversation_id`，每条消息保存角色、文本、轮次、时间和状态：

- 用户消息：最终转录后落库，必要时标注转录不确定性。
- AI 消息：流式追加；若被打断，应标记 `interrupted`，而不是当作完整回答。
- 语音状态球：麦克风音量取处理后的真实输入；AI 音量取实际播放 PCM 的 RMS/包络值，而非收到数据的音量或预设动画。
- 左右气泡持续追加，页面可滚动查看多轮。
- 退出语音模式：关闭麦克风轨道、音频处理、连接或会话订阅，停止本地播放并取消当前回答；不删除 SQLite 文字历史。
- 重开原会话：从 SQLite 加载消息；级联直接复用原来的历史拼接逻辑，原生服务则创建新实时连接并注入必要的历史文本与摘要。

对于原生 API，文字记录可以来自输入转录和输出文本事件，但应区分“实际语音转录”和“模型计划说出的文本”。遇到插话或播放中断，二者不一定相同。

本地保存的历史不等于供应商仍保留完整音频上下文。 例如 Qwen-Audio 3.1 Realtime 官方明确限定了内部音频历史最多 50 轮、累计 300 秒；长期会话应该依靠 SQLite 和应用自己的摘要/历史重新注入机制。

## 七、建议交给开发者的技术方案

### 第一阶段：不替换模型，补全连续语音基础设施

保留 SQLite、MiMo、TokenDance、现有对话接口，把网页音频入口从 `MediaRecorder + 手动结束` 改为持续采样和实时事件控制。

推荐的数据流为：

```
浏览器（持续麦克风）
  AudioWorklet → PCM 小帧
  浏览器 AEC / 降噪
       ↓ WebSocket
FastAPI 会话控制
  VAD + 判停模块
       ↓
在线流式 ASR（或先复用 SenseVoice 自动切段）
       ↓
现有 TokenDance 文字对话
       ↓
现有 MiMo TTS 流式输出
       ↓
浏览器 PCM 播放队列

同时运行：
插话检测 → 播放停止 → 后端取消
文字事件 → SQLite → 多轮聊天气泡
```

其中 AudioWorklet 用于较稳定的小帧采集和音量统计；实际向供应商发送多少毫秒一包，需遵守其协议。例如 Seeduplex 建议 20ms 音频帧，而 Qwen-Audio WebSocket 文档建议约 100ms 分片，不能强制所有 API 使用同一个大小。

docs.volcengine.com+1



已有后端 VAD 的算法与模型可以复用，但网页端应有自己独立的连接、采样缓冲与状态；不要复用 AtomS3R 设备的流状态。

### 第二阶段：增强自然断句和打断

先用实际音频数据比较：

- Silero + 固定候选停顿。
- Silero + Smart Turn。
- 云流式 ASR 的 endpointing。
- Qwen `smart_turn_v2` 或其他原生服务的内建轮次判断。

这里不是比较单一的“静音阈值”，而是同时比较：用户思考时的抢话概率、说完后的等待时间、短附和误取消概率、普通外放的成功插话概率。

### 第三阶段：做同条件原生语音对照

先试 Qwen-Audio 3.1 Realtime Flash，再试 Seeduplex。 用同一台电脑、同一浏览器、同一扬声器和麦克风、同一组中文测试语句，比较级联与原生路线。

如果原生方案明显更快、双讲可靠、中文角色表现和复刻音色可接受，并且账单符合预算，再考虑迁移。否则保留已经建立的级联系统，并把测试得到的判停和音频处理经验用于原架构。

## 八、实际要测哪些指标

| 指标                   | 测量方法                                       | 为什么必须测                       |
| ---------------------- | ---------------------------------------------- | ---------------------------------- |
| 端到端接话时间 P50/P95 | 从用户实际停止发声到扬声器发出 AI 首个有效声音 | 比供应商宣传首包指标更接近真实体验 |
| ASR 最终确定时间       | 记录候选判停、最终转录事件                     | 区分 ASR 慢与轮次判断慢            |
| 首段可播报文字时间     | LLM 从请求到首段完整可读文字                   | 首 Token 时间不能代表 TTS 可以开始 |
| TTS 首包与播放排队     | 记录首包生成、收到、真正播出                   | 分辨供应商延迟与本地缓冲延迟       |
| 插话响应时间           | 用户开口到本地 AI 音频真正停止                 | 测量真正的打断体验                 |
| 误打断率               | 键盘、咳嗽、“嗯”、AI 回声、电视测试            | 检查过度敏感                       |
| 抢话率                 | 中文犹豫、换气、句中长停顿测试                 | 检查自然断句                       |
| 成本与资源             | 服务端 usage、云平台账单、RSS、CPU             | 判断 2核2GB 和 API 费用是否可接受  |

不能只测安静环境里的一句“你好”。最有价值的是四组录音：普通聊天、思考停顿、AI 播放期间真人插话、AI 外放加环境干扰。手机外放还应独立测试，因为桌面 Chrome 的 AEC 表现不代表移动端浏览器。

网络方面，至少分别记录设备到服务器、服务器到 ASR/LLM/TTS 厂商的往返延迟。若 TokenDance 网关增加跨地区转发，或者长上下文使 LLM 首段变慢，仅换一个“快速模型”未必有效。供应商排队、实时模型的内部分句策略和音频首包能力属于应用端不能直接控制的部分，只能选型、配置和验证。

## 九、你需要决定什么，开发者负责什么

| 你需要决定或提供                                        | 开发者应负责                           |
| ------------------------------------------------------- | -------------------------------------- |
| MiMo 克隆音色必须高度一致，还是可以接受相似的新复刻音色 | 验证目标服务的复刻权限、质量和延迟     |
| 可接受的月度 API 预算、优先使用国内还是国际供应商       | 列出实际 SKU、地域、账单和持续收音成本 |
| 最常用的设备、浏览器、外放方式                          | 测 AEC 双讲、采样格式和浏览器兼容性    |
| 对误打断和自然停顿的取舍偏好                            | 实现候选插话、确认、取消和误判恢复     |
| 是否允许保存用于质量评估的测试音频                      | 设计测试、埋点、隐私与数据保留策略     |
| 云服务器最终系统版本和实际配置                          | 在 Linux 上进行实际资源及网络验证      |

现阶段不用你提供全部代码即可完成架构判断；但要准确定位现有延迟，开发者最终需要看到录音入口、TTS 播放队列、现有取消接口及对应的时间日志。当前 TokenDance 具体文字模型、MiMo TTS 的实际计费 SKU、现有网络路径都尚未确定，因此不应虚构一份完整的现有级联月费。

## 最终决策

继续级联作为主线，原生实时语音作为替代实验。

现在最值得开发的不是重新接一个更贵的语音大模型，而是将“持续收音、判停、全双工插话、PCM 队列取消、历史同步”整理成独立的网页语音会话层。它能直接补足现有缺口，而且将来换成 Qwen、Seeduplex 或 OpenAI Realtime 时也不会白做。

如果你的优先级转变为极致自然的接话与全双工，并且新音色可以接受，则优先测试 Qwen-Audio 3.1 Realtime Flash 的 `smart_turn_v2` / 说话人增强，再用 Seeduplex 3.0 验证中文双讲及抗干扰能力。

已经有可靠依据的是这些 API、协议能力和官方价目；尚不能提前保证的是你这套实际浏览器、麦克风、扬声器和网络下的打断可靠性及端到端响应时间。这些效果应由上述同条件测试决定，而不是根据模型类别决定。
