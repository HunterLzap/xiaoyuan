# 个人知识库（RAG）设计

日期：2026-11-07。方案：**混合 C**。目标云服务器 2 核约 1.87GB、无 swap——重活走百炼云端，本机只做存储与检索。本文是个人知识库模块的设计与分期，产品范围仍以 [roadmap](roadmap.md) P1 为准，实现事实记 [progress](progress.md)。

## 2026-11-08 多库与归属（当前有效）

用户已确认个人知识库做**多独立库**（左库列表＋右文档表，见图3），库是硬归属：

- 数据模型在现有单库基础上增量：新增 `kb_libraries`（id、name、created_at），`kb_documents` 加 `library_id`；旧 `group_name` 保留为可选标签，不再作为检索边界。
- 检索硬过滤：关键词/向量/覆盖率三处 SQL 都 JOIN `kb_documents`，统一加 `d.library_id IN (所选库)`。**过滤必须在服务端 SQL 层，不能靠提示词。此项尚未实跑核实**：FTS 若先取 top-k 再过滤会漏检，需保证“先按库过滤、再取 top-k”，实测通过前不下结论。
- 迁移：启动时 `ALTER TABLE` 加列，把现有文档归入“默认知识库”并回填 `library_id`；需停机窗口，属 Lead 调度，不在文档同步阶段执行。
- 助手配置里选的是 library_id 列表；多库时检索只在选中库内进行。下文“按 group 检索”的旧描述作为历史基线，按本节扩展。

## 1. 已确认决策（用户）

- 采用混合方案 C：本地免费部分优先，智能部分用云端模型。
- 图片/扫描件 → 云端视觉模型识别（不在本机跑 OCR）。
- embedding → 云端（百炼），本地只在 SQLite 存向量并做余弦检索。
- 生成 → 复用现有对话模型，允许把检索结果接进对话主链路（用户已同意改 realtime/service/llm）。
- 数据洞察 → 要做（本地审计 + 看板）。
- 不在服务器安装/常驻视觉、embedding、rerank 等大模型。

## 2. 分环节设计

| 环节 | 实现 | 类型 | 依赖 |
| --- | --- | --- | --- |
| 文档解析 | TXT/MD/DOCX 本地解析；PDF 文字版用 pypdf | 本地库（pypdf 7.0.0 已装项目 .venv） | pypdf |
| 图片/扫描件 | 云端视觉模型读图取文字 | 模型能力（百炼，按量） | 百炼视觉模型（型号/计费待核实） |
| 清洗 | 空白归一、去空字符、去重复段、去页眉页脚 | 本地规则 | 无 |
| 切片 | 规则切片 ~900 字/重叠 100；后续可加语义切 | 本地规则（语义切依赖 embedding） | 无 |
| 索引 | 关键词 FTS5（已有）+ 向量（云端 embedding→本地存向量） | 本地存储 + 模型能力 | 百炼 qwen3.7-text-embedding，1024 维（已实际使用） |
| 召回 | BM25 + 向量余弦，RRF 融合 top_k（≤8） | 本地计算 | 无 |
| 生成 | top_k 片段拼进现有对话模型，带出处回答，只注入片段不塞整篇 | 模型能力 | 现有对话模型 |
| 洞察 | 本地审计表记录检索/工具调用 + 看板 | 本地 | 无 |

## 3. 数据模型（SQLite，沿用 data/personal_kb.sqlite3）

- 多库见 2026-11-08 节：新增 `kb_libraries` 与 `kb_documents.library_id`；下列为单库基线。
- 保留现有 `kb_documents` / `kb_chunks` / `kb_search`(FTS5)。
- 新增 `kb_vectors`：chunk_id、doc_id、model、dim、vector( float32 BLOB)、created_at。
- 新增 `kb_audit`：id、ts、surface(kb_search|tool_call)、session_id、query_summary(截断脱敏)、hit(bool)、top_k、sources(json: doc_id/filename/ordinal/score)、elapsed_ms、status、error_code。
- 入库：解析→清洗→切片→逐段调云端 embedding→存向量，状态 processing→ready；失败保留旧资料。
- 查询：问题调云端 embedding→本地余弦 top_k→与 BM25 结果 RRF 融合→带来源。
- 断网/云端不可用：明确「知识库暂不可用/未检索到」，不编造。

## 4. 接口（在既有基础上增量）

- 上传/替换：生成向量；状态字段区分 processing/ready/failed。
- 检索：`POST /api/knowledge/personal/search` 增加 `hybrid` 与返回 score/hit/来源。
- 洞察：新增 `GET /api/insights/kb`、`GET /api/insights/tools`（字段由核心开发定稿）。

## 5. 对话接入（冻结链路，用户已同意）

- 实时：`realtime.py` 的 tools 列表加入 `search_personal_knowledge`；模型发起→服务端校验执行→片段回填（标注「资料非指令」）。
- 分模型：`service.py` / `llm.py` 的 tool_calls 回合。
- 出处：`schemas.py` 消息字段加 knowledge 来源；前端标注文件名/片段。
- 只注入 top_k 片段，不塞整篇；改动最小侵入，保留现有语音/打断/停止行为，改前备份、改后回归语音链路。

## 8. API 配置与洞察交互（用户四张参考图）

以参考图的信息结构与操作流程为准，沿用项目灰阶明暗主题；示例 API、问题和答案不作为项目数据。

- API 管理：左侧搜索、接口列表与新增/编辑/删除；右侧接口页签、可视化配置/JSON 定义切换、Method/URL/接口描述、测试/保存。输入表支持名称、描述、类型、必填、默认值、启用；同时提供 Params/Headers/鉴权/Body 和输出字段定义。可视化与 JSON 共用同一份定义，无法无损转换的内容应明确提示，不能丢弃。输出定义用于字段说明及结果映射，不伪造上游未返回的字段。
- 洞察列表：问题、时间、会话/渠道、回答类型、答案摘要、检索/调用状态及详情入口。没有实际评测时准确度显示未评测，检索分数不能当作准确率；不因参考图包含工单或 FAQ 就新增对应业务。
- 洞察详情：展示触发问题、最终实际回答、会话/轮次及调用链；答案对比页展示机器人回答和来源，正确答案可人工录入作为评审参考，未填写显示空态，不自动覆盖知识库或启用训练。
- 回溯片段：记录当时召回片段正文快照、文档 ID/版本、文件名、页码（可获得时）、片段号、检索方式及原始分数类型、是否实际送入模型；区分召回片段与最终引用。替换或删除资料后，历史快照仍须能解释当时回答；原文已不存在时明确提示，不能链接到新版本冒充旧出处。
- API 调用详情：关联触发问题、session_id/turn_id/call_id；显示工具名、方法/地址、脱敏参数/请求与响应、HTTP 状态、业务结果、耗时、错误/取消状态及最终回答。手动调试标为手动来源，不能伪造为模型自动调用。
- 解析/OCR/供应商报错作为失败诊断独立保存，不能混入知识片段或被召回为知识。诊断和请求/响应展示均脱敏，正文按需读取并限制大小，避免列表加载大量片段或响应。
